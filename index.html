01 / SQL / Backend

주식 테이블 하나를 위해 최근 90일 분석 약 17만 행을 정렬하고 있었습니다.

문제/원인
최신 결과만 필요했지만 과거 분석 전체를 정렬했고, 한 종목에서만 필요한 예측·최근 흐름·대표뉴스까지 100종목 목록 조회에 섞여 있었습니다.
변경
최신 분석일을 SQL에서 먼저 제한하고, 목록 조회와 단일 종목 조회의 책임을 분리했습니다.
결과

02 / Data Pipeline

이미 처리한 뉴스인지 DB가 아니라 실행 중 생성되는 CSV 파일을 보고 판단하고 있었습니다.

문제/원인
CSV를 정리하면 DB에 이미 저장된 기사도 다시 크롤링할 수 있었고, 현재 실행 자료와 과거 처리 이력이 한 파일에 섞여 있었습니다.
변경
DB를 처리 상태의 기준으로 바꾸고, 완료된 기사는 제외하고 본문만 있는 기사는 DB 값을 재사용하며 신규 기사만 다시 요청하도록 분리했습니다.
결과
실행 파일의 존재 여부와 관계없이 DB 상태를 기준으로 필요한 단계만 재실행하도록 바꿨습니다.

03 / NLP / Data Quality

형태소 분석기를 붙였는데 원문에 없는 의미가 모델 입력으로 들어가고 있었습니다.

문제/원인
실제 댓글을 검수하던 중 확인·강조 표현 `-잖-`이 일부 문장에서 `않/VX`로 분석되는 사례를 발견했습니다.
변경
token의 원문 위치를 다시 대조해 관찰된 오분석만 제외하고, `삼전`, `자사주`, `액면분할` 같은 주식 커뮤니티 표현을 Kiwi 사용자 사전에 보완했습니다.
결과
라이브러리 출력을 그대로 신뢰하지 않고 실제 모델 입력을 다시 확인하는 검수 단계를 만들었습니다.

04 / Model Serving

모델 파일 하나만 저장해서는 같은 추론 조건을 보장하기 어려웠습니다.

문제/원인
모델 파일과 다른 TF-IDF vocabulary, tokenizer 설정, 학습 데이터셋이 섞이면 같은 이름의 모델이라도 동일한 서비스 추론 구성이라고 보기 어려웠습니다.
변경
학습된 TF-IDF와 Ridge, 모델·tokenizer 버전, 데이터셋 기간을 하나의 versioned artifact로 묶고 로드 시 feature 차원과 객체 상태를 검증했습니다.
결과
서비스 추론이 단순 파일 경로가 아니라 검증 가능한 모델 식별 정보와 입력 계약을 기준으로 실행되게 했습니다.

05 / Automation / Reliability

자동화에서 먼저 정한 것은 “언제 실행할지”보다 “어디서 멈출지”였습니다.

문제/원인
앞 단계가 실패했는데 뒤 분석까지 계속되거나, 이전 실행이 끝나기 전에 다음 실행이 시작되면 불완전한 결과가 후속 단계로 전파될 수 있었습니다.
변경
단계별 결과를 확인해 실패 지점에서 후속 실행을 중단하고, file lock과 실행 상태·실패 위치 기록을 추가했습니다.
결과
중복 실행 차단 · 실패 stage 기록 · 대상 0건 정상 종료를 전체 pipeline 계약으로 관리했습니다.

06 / LLM Integration

LLM이 모델 결과를 다시 판단하지 못하게 했습니다.

문제/원인
모델 수치와 키워드를 자유롭게 설명하게 두면 계산하지 않은 미래 전망, 투자 권고나 점수 우열까지 그럴듯하게 추가할 수 있었습니다.
변경
결과 의미와 사용할 evidence는 코드에서 먼저 검증·확정하고, LLM에는 제한된 정형 데이터만 전달해 문장화 역할로 좁혔습니다.
결과
미래 전망 · 투자 권고 · 직접 점수 비교를 금지하고, 모델이 계산한 범위 안에서만 설명하도록 계약을 만들었습니다.
