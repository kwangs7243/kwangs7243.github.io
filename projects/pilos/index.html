01 / 프로젝트 개요

댓글이 긍정적인지가 아니라, 실제 개인투자자 수급과 어떤 표현이 함께 나타났는지 분석했습니다.

프로젝트 질문

같은 종목·거래일에 작성된 댓글 표현과 그날의 개인투자자 매수·매도 우세 사이에는 어떤 통계적 연관성이 있을까?

접근

종목·거래일별 댓글을 전처리하고 Kiwi로 토큰화한 뒤 하나의 일별문서로 합쳐 TF-IDF 벡터를 만들었습니다. 같은 종목·거래일의 개인투자자 매수·매도 수급 기준값을 정답값으로 연결하고, 방향별 Ridge Regression으로 댓글 표현과 수급 우세 사이의 연관 가중치를 학습했습니다.

서비스 결과

학습된 Vectorizer와 Ridge를 신규 일별 댓글 문서에 적용해 다음 결과를 제공합니다.

  • 수급 방향별 댓글 표현 연관 점수
  • 결과에 크게 기여한 주요 표현
  • 과거 동일 모델 결과분포에서의 0~100 상대 신호
  • 실제 개인투자자 수급 상태와 일별 LLM 설명
  • 단일 댓글에 대한 두 방향 모델 반응 비교

분석 범위

이 프로젝트는 일반적인 긍정·부정 감성분류가 아닙니다. 미래 주가·수급을 예측하거나 실제 매수·매도 확률을 계산하지 않으며, 투자 종목이나 매매 시점을 추천하지 않습니다. 댓글이 실제 매매 행동을 일으켰다는 인과관계도 주장하지 않습니다.

핵심 데이터종목·거래일별 온라인 댓글 + 같은 종목·거래일의 개인투자자 일별 매수·매도 수급

02 / 실제 서비스 화면

분석 과정의 결과를 실제 사용자 화면까지 연결했습니다.

아래 화면은 프로젝트에서 실제로 구현한 서비스 화면입니다. 포트폴리오용 가상 UI를 새로 만들지 않고, 분석 결과가 어디에서 어떻게 사용됐는지를 보여주는 화면만 사용합니다.

03 / 프로젝트 개념도

학습 구조와 서비스 추론 구조를 분리해 이해합니다.

03-A / 모델 학습 구조

댓글 표현을 입력으로, 같은 날 개인투자자 수급을 정답으로 연결했습니다.

  1. 종목·거래일별 댓글
  2. 전처리
  3. Kiwi 토큰화
  4. 종목·거래일별 일별문서
  5. TF-IDF
  6. 학습 입력 X
  1. 같은 종목·거래일의 개인투자자 매수·매도 수급
  2. 수급 기준값
  3. 학습 정답 Y
  1. X + Y
  2. 방향별 Ridge 후보 학습·검증
  3. 최종 Ridge text-only 모델
  4. Vectorizer + Ridge Artifact

댓글 TF-IDF가 Ridge의 입력이고, 개인투자자 수급 기준값은 학습 정답입니다. 두 데이터는 같은 종목·거래일을 기준으로 연결됩니다. 모델은 댓글이 미래 수급을 만든다고 학습하는 것이 아니라, 보유 Dataset에서 댓글 표현과 당일 수급 우세가 함께 나타난 통계적 관계를 학습합니다.

03-B / 서비스 추론 구조

서비스에서는 신규 종목·거래일의 댓글 문서를 학습된 Vectorizer와 Ridge에 다시 통과시킵니다.

  1. 신규 댓글
  2. 전처리 / Kiwi
  3. 종목·거래일별 일별문서
  4. 학습된 TF-IDF
  5. 학습된 방향별 Ridge
  6. 모델 원출력 + 주요 단어 contribution
  7. 입력 품질 / 결과 제공 상태 판정
  8. DB 저장
  9. Calibration
  10. 0~100 상대 신호
  11. 검증된 정형 Evidence
  12. LLM 일별 설명
  13. Flask 서비스

서비스 시점의 개인투자자 수급 데이터는 Ridge의 텍스트 추론 입력으로 들어가지 않습니다. 실제 수급은 서비스 화면과 일별 설명의 관측 상태로 함께 사용되지만, 신규 댓글의 Ridge 계산 자체는 학습된 Vectorizer와 댓글 문서를 기준으로 수행됩니다.

05 / 데이터와 모델을 만드는 과정

모델을 고르기 전에, 실제 댓글이 어떤 입력으로 바뀌는지부터 확인했습니다.

이 프로젝트의 모델 입력은 종목·거래일별 댓글입니다. 따라서 모델 종류보다 먼저 댓글이 전처리·토큰화·벡터화되는 과정에서 의미가 깨지지 않는지 확인하고, 이후 같은 날짜의 수급 기준값과 연결해 모델 후보를 검증했습니다.

05-A / 실제 댓글 입력 검수

형태소 분석 결과를 실제 원문과 다시 대조했습니다.

  1. 댓글 원문
  2. 기본 전처리
  3. Kiwi 형태소 분석
  4. POS/불용어 필터
  5. 실제 token 검수
  6. 종목·거래일별 일별문서

발견한 문제

삼성전자 실제 댓글을 벡터화해 상위 TF-IDF 표현을 확인하던 중, 확인·강조 어미 -잖-이 일부 문장에서 않/VX로 분석되는 사례를 발견했습니다. POS만 보면 정상적인 보조용언처럼 보이기 때문에 단순 품사 필터로는 오분석 여부를 구분하기 어려웠습니다.

대응

  • Kiwi token의 시작 위치와 길이로 원문 substring을 다시 확인
  • 원문이 잖인데 않/VX로 분석된 관찰 사례만 선택적으로 제외
  • 삼전, 영차, 자사주, 액면분할, 십만전자 등 프로젝트 Dataset에서 반복되는 표현을 사용자 사전에 보완

의미

형태소 분석 라이브러리를 사용했다는 사실보다, 실제 모델 입력을 다시 확인하고 관찰된 오류를 수정한 과정을 중요하게 봤습니다. 이 규칙이 모든 한국어 형태소 오류를 해결한다고 보지는 않습니다.

05-B / TF-IDF와 sparse 입력

일별 댓글 문서를 TF-IDF 희소 벡터로 변환했습니다.

  1. 같은 종목·거래일 댓글 token
  2. 하나의 일별문서
  3. TF-IDF
  4. Ridge 입력 X

구현 포인트

  • 학습 Dataset의 일별문서를 기준으로 TF-IDF vocabulary와 IDF 학습
  • 서비스 추론에서도 학습 때 저장한 동일 Vectorizer 사용
  • 검수 코드에서는 sparse row를 매번 dense 배열로 풀지 않고 row.indices, row.data의 non-zero 값만 확인

댓글별 TF-IDF 상위 표현을 검수하던 코드가 sparse row를 toarray().flatten()으로 전체 dense 배열로 변환하고 있었습니다. 이를 실제 값이 존재하는 feature만 읽도록 수정했습니다. 별도 benchmark를 남기지 않았기 때문에 특정 배수의 성능 향상으로 표현하지 않습니다.

05-C / 모델 후보와 두 가지 검증

미래 예측 성능과 당일 연관성 재현을 같은 검증으로 설명하지 않았습니다.

비교 후보

  • Ridge
  • ElasticNet
  • text-only
  • 댓글 수 feature를 추가한 후보

1) 워크포워드 검증

과거 구간으로 학습하고 이후 월을 검증해 시간이 지나며 댓글량·어휘·수급 분포가 달라졌을 때 성능이 얼마나 흔들리는지 확인했습니다.

  • 검증 구간: 2026년 4월, 5월, 6월, 7월 1~24일
  • 40개 후보 × 2개 방향 × 4개 Fold = 320회 평가
  • 최종 text-only Ridge alpha=1 평균 R² — Positive: 0.0481, Negative: 0.0503

2) 날짜 그룹 랜덤 검증

보유 Dataset 내부에서 같은 시기의 댓글 표현과 당일 수급 관계가 어느 정도 재현되는지 별도로 확인했습니다.

  • 각 월의 고유 날짜 약 20%를 validation 날짜로 선택
  • 같은 날짜의 모든 종목을 train 또는 validation 한쪽에만 배치
  • Positive/Negative가 같은 날짜 split 사용
  • 5개 seed 반복
  • TF-IDF vocabulary와 IDF도 각 fold의 train 데이터로만 fit

최종 text-only Ridge alpha=1 평균 validation R² — Positive: 0.206797, Negative: 0.221247

해석

날짜 그룹 랜덤 검증에서 수치가 더 높았다는 사실을 모델이 새로 좋아졌다고 해석하지 않았습니다. 시간 순서를 강제한 워크포워드에서 성능이 크게 낮아진 결과와 함께 보면서 동시점 연관성은 일부 재현되지만 시간 분포 변화에는 민감하다고 해석했습니다.

05-D / 최종 Ridge text-only 선택

조금 높은 점수보다 단순하고 일관된 서비스 입력 계약을 선택했습니다.

판단 근거

Negative 방향에서 댓글 수 feature를 추가한 Ridge의 날짜 그룹 랜덤 평균 R²가 text-only보다 약간 높았습니다.

  • text + 댓글 수: 약 0.2215
  • text-only: 약 0.2212
  • 평균 이득: 0.000227
  • 5개 seed 중 1개에서는 text-only보다 악화

워크포워드에서도 댓글 수 feature의 견고한 추가 효용을 확인하기 어려웠습니다.

최종 선택

Positive / Negative 모두 Ridge text-only, alpha=1

이유

현재 Dataset에서 댓글 수 feature의 추가 이득이 오차 수준에 가까웠고 방향별 입력 구조를 다르게 유지해야 할 근거가 부족했습니다. 따라서 두 방향의 입력 계약을 단순하게 통일했습니다.

댓글 수가 일반적으로 쓸모없는 feature라는 뜻이 아닙니다. 이번 Dataset과 검증 조건에서 견고한 추가 효용을 확인하지 못했다는 판단입니다.

06 / 실험 모델을 서비스 계약으로 만드는 과정

모델이 계산되는 것과, 서비스가 그 결과를 신뢰하고 제공하는 것은 다른 문제였습니다.

노트북에서 Ridge를 학습하는 것만으로 서비스가 완성되지는 않았습니다. 어떤 Vectorizer와 데이터로 학습된 모델인지 식별하고, 입력 품질이 부족한 결과를 구분하고, Backend와 LLM이 같은 모델 결과를 바라보도록 서비스 계약을 만들었습니다.

06-A / 재현 가능한 model artifact

모델 identity와 입력 계약을 함께 저장했습니다.

Ridge .pkl만 남아 있으면 어떤 TF-IDF vocabulary, tokenizer 설정, Dataset 기간으로 학습했는지 파일만 보고 확인하기 어렵습니다. 서로 다른 조건의 객체가 섞이면 같은 모델 이름이어도 동일한 추론 구성이라고 보기 어렵습니다.

하나의 versioned artifact에 다음을 같이 저장했습니다.

  • artifact schema version
  • model name / direction / version
  • tokenizer version
  • Dataset start / end
  • fitted TfidfVectorizer
  • fitted Ridge

로드 시 다음을 검증했습니다.

  • 실제 학습된 Vectorizer와 Ridge인지
  • TF-IDF feature 수와 Ridge coefficient 수가 같은지
  • coefficient / intercept가 유효한 값인지
  • Dataset 기간과 metadata가 계약을 만족하는지

서비스 추론은 임의의 모델 파일 경로가 아니라 검증 가능한 model identity + 입력 계약을 기준으로 실행되게 했습니다.

06-B / 계산 가능과 제공 가능을 분리

숫자가 계산됐다고 정상 서비스 결과로 보지는 않았습니다.

입력 문서에 모델 vocabulary와 겹치는 단어가 거의 없어도 Ridge는 숫자를 반환할 수 있습니다. 이 값을 다른 정상 결과와 같은 상태로 노출하면 계산 성공과 분석 근거 충분성을 혼동하게 됩니다.

  • recognized_feature_count
  • unique_token_count
  • vocabulary_coverage
  • inference_status — ready / insufficient_features

활성 artifact 기준 미완료 대상만 조회하고, 같은 daily_document + artifact 조합의 결과 중복을 방어했습니다. 추론 대상이 0건이면 실패가 아니라 정상 no-op 종료로 처리하고, 자동 추론 허용 시작일 이전의 과거 데이터 무제한 backfill을 방지했습니다.

DB row의 존재 여부와 사용자에게 제공 가능한 분석 상태를 분리했습니다.

06-C / active model identity와 Flask 조회 계약

생산자와 소비자가 같은 모델 identity와 상태 계약을 사용하게 했습니다.

Flask가 특정 artifact ID를 고정해서 조회하면 서비스 모델이 바뀐 뒤에도 과거 artifact 결과를 최신 결과처럼 읽을 수 있습니다.

  • 목록·상세·보고서·단일 댓글이 공통 active model identity 사용
  • 최신 일별문서 + 활성 artifact 기준으로 조회
  • 공개 응답에서 내부 artifact_id를 서비스 의미로 노출하지 않음
  • 추론 대기 / 보고서 생성 대기 / 수급 갱신 대기 / 제공 가능 상태 구분

결과를 만드는 생산자와 화면에서 읽는 소비자가 같은 모델 identity와 상태 계약을 사용하게 했습니다.

06-D / Calibration과 사용자용 상대 신호

모델 원출력을 같은 모델의 과거 분포 안에서 상대화했습니다.

  1. Ridge 원출력
  2. 동일 모델의 과거 기준분포
  3. 현재 값의 상대 위치 계산
  4. 0~100 서비스 신호

0~100 값은 같은 모델 조건으로 생성된 과거 결과분포에서 현재 출력이 어느 위치에 있는지를 표현한 상대 결과입니다.

  • 매수 확률 / 매도 확률 아님
  • 모델 정확도 아님
  • 투자 점수 아님
  • 미래 개인투자자 수급 예측 아님

06-E / LLM의 역할을 문장화로 제한

LLM이 모델 결과를 다시 판단하지 못하게 했습니다.

모델 수치와 keyword를 자유롭게 설명하게 두면 모델이 계산하지 않은 미래 전망, 투자 행동, 점수 우열이나 일부 keyword를 전체 근거처럼 확대하는 표현이 추가될 수 있었습니다.

LLM 이전 애플리케이션 코드

  • keyword contribution 방향 검증
  • 수치 자료형과 유효성 검증
  • 전달 evidence 개수 제한
  • Unicode와 key 순서 정규화
  • deterministic JSON 생성
  • input hash 생성

LLM 계약

  • 미래 주가·수급 전망 금지
  • 투자 권고 금지
  • Positive/Negative 점수 직접 우열 비교 금지
  • 상위 keyword만으로 전체 결과 단정 금지
  • 제공된 evidence 밖의 의미 추가 금지
  • 정해진 JSON schema로 응답

애플리케이션이 결과의 의미와 근거를 먼저 확정하고, LLM은 검증된 정형 evidence를 사용자 문장으로 정리하는 계층으로 제한했습니다.

LLM 오류 가능성을 완전히 제거했다고 표현하지 않습니다. 입력·출력 범위를 제한하고 검증 가능한 계약으로 좁힌 구조입니다.

개별 Job을 연결하는 것보다, 실패했을 때 어디서 멈출지를 먼저 정했습니다.

  1. 댓글 수집
  2. 댓글 전처리

  4. 종목·거래일별 일별문서 생성
  5. 개인투자자 수급 수집
  6. 모델 추론 / 결과 저장
  7. calibration·보고서 입력 구성
  8. v13 LLM 일별 설명 생성

앞 단계가 실패하면 해당 결과를 전제로 하는 downstream stage를 실행하지 않습니다.

전체 pipeline에서 추가한 계약

단계별 성공/실패 확인

앞 단계가 실패하면 해당 결과를 전제로 하는 downstream stage를 실행하지 않습니다.

중복 실행 방지

non-blocking file lock으로 이전 pipeline이 실행 중일 때 새 실행이 겹치지 않게 했습니다.

실행 상태 저장

  • running / completed / failed
  • 시작/종료/소요시간
  • 중단 stage
  • failure type / message
  • stage별 처리 요약

대상 0건을 정상 상태로 처리

새로운 추론·보고서 대상이 없는 경우 불필요한 실패로 만들지 않습니다.

부분 외부 데이터 장애 격리

장중 수급 API에서 한 종목의 필수 투자자 분류가 누락됐을 때, 해당 종목 하나 때문에 전체 대상 수집을 실패시키지 않도록 범위를 나눴습니다.

  1. 완전한 종목 → 계속 처리
  2. 불완전한 종목 → warning + skip
  3. 모든 대상 불완전 → 전체 실패

skip 수는 Job 결과에 남겨 부분 성공을 숨기지 않습니다.

자동화 범위에서 제외되는 것

  • 모델 자동 재학습
  • RAG / Chroma 전체 적재

위 기능이 최상위 자동화에 포함된 것처럼 표현하지 않습니다.

최상위 자동화 통합 시점에 전체 테스트와 별도 pipeline 상태·로그 계약 테스트를 수행했고, 실제 DB/외부 API 경계도 확인했습니다. 테스트 개수는 해당 PR 시점 기록으로만 사용하고 현재 전체 테스트 수처럼 확대하지 않습니다.

09 / 결과와 한계

서비스까지 연결했지만, 모델의 해석 범위와 검증 한계도 함께 남겼습니다.

  • 2025-01-02 ~ 2026-07-24 Dataset으로 서비스 모델 v4 재학습

해석

같은 전체 기간에서 날짜를 그룹 단위로 나눈 검증에서는 당일 연관성이 일부 재현됐지만, 과거에서 이후 월로 이동하는 워크포워드에서는 성능이 크게 낮았습니다. 댓글량·어휘·수급 분포 변화에 민감하다는 한계로 해석했습니다.

또한 날짜 그룹 랜덤 검증의 Ridge는 학습 R²와 validation R²의 격차가 두 방향 모두 약 0.50 수준이므로 과적합 위험이 사라졌다고 보지 않습니다.

서비스/데이터 검증 근거

  • 모델 추론·v13 보고서 운영 계약 PR에서 전체 테스트와 실제 DB 품질값/보고서 적재 상태를 재검증
  • Flask 서비스 계약 PR에서 비DB 테스트와 실제 DB 읽기 요청 확인
  • 최상위 자동화 PR에서 pipeline 상태·로그 계약과 DB/외부 API 경계 확인

정량 테스트 개수는 각 PR 시점의 검증 이력으로만 사용하고 프로젝트 전체의 현재 품질 점수처럼 표현하지 않습니다.

한계

검증 결과를 서비스 의미보다 크게 해석하지 않았습니다.

  • 교육 과정의 제한된 기간과 Dataset으로 수행한 프로젝트
  • 미래 주가·수급 예측 모델이 아님
  • 댓글과 실제 매매 행동의 인과관계를 증명하지 않음
  • 댓글 표현의 사실 여부나 진위를 판단하지 않음
  • 시간 변화에 따른 분포 이동에서 성능 저하 확인
  • 외부 API, DB, LLM 환경이 없으면 전체 서비스 흐름을 그대로 재현하기 어려움
  • 모델 자동 재학습과 production 수준 drift monitoring은 현재 범위에 포함되지 않음

이 프로젝트의 성과는 높은 예측 정확도를 주장하는 데 있지 않습니다. 댓글 표현과 당일 수급의 연관성을 제한된 범위에서 모델링하고, 그 결과를 재현 가능한 모델·품질 상태·사용자 결과·LLM 설명·자동화 흐름까지 연결해 본 경험에 있습니다.

10 / 회고

모델을 만드는 것보다, 그 결과가 어떤 조건에서 서비스될 수 있는지를 더 많이 배웠습니다.

처음에는 전처리와 모델 성능처럼 분석 과정 자체에 집중했습니다. 하지만 실제 서비스 흐름으로 연결하면서 같은 모델이라도 어떤 Vectorizer와 데이터로 학습됐는지, 입력 근거가 부족한 결과를 정상 결과로 보여줘도 되는지, LLM이 어디까지 해석해도 되는지, 앞 단계가 실패했을 때 뒤 단계가 계속 실행돼도 되는지가 더 큰 문제가 됐습니다.

그래서 프로젝트 후반에는 모델 파일 하나보다 artifact 계약, 숫자 하나보다 결과 상태, 개별 Job 하나보다 실패 경계를 가진 전체 실행 흐름을 더 중요하게 다루게 됐습니다.

이 경험을 통해 백엔드에서 AI 기능을 연결한다는 것은 모델 API를 호출하는 데서 끝나는 것이 아니라, 입력·출력의 의미와 상태, 재실행, 실패 범위까지 서비스가 이해할 수 있는 계약으로 만드는 일이라는 방향을 잡게 됐습니다.
