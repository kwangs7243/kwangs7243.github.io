01

프로젝트 개요

댓글 표현과 당일 개인투자자 매수·매도 우세 관계를 학습했습니다

PILOS — 종목 댓글과 개인투자자 매매 우세의 통계적 연관 분석 서비스

종목·일자별 온라인 댓글 표현과, 같은 날 개인투자자의 매수량과 매도량 중 어느 쪽이 상대적으로 우세했는지를 연결해 두 데이터의 통계적 연관성을 분석합니다. 이때 매수와 매도의 상대적 우세를 수치로 나타낸 값이 ‘개인투자자 매수·매도 우세도’입니다.

개인 역할 요약

4인 팀의 팀장으로 전체 기술 관리를 맡았습니다. 댓글 데이터 처리와 TF-IDF 기반 모델 파이프라인, Ridge 학습·추론, 결과 변환과 일별 댓글·매매 해설 연동, 댓글 수집부터 해설 생성까지 이어지는 실행 흐름 통합을 담당했습니다.

분석 범위

일반적인 긍정·부정 감성분류가 아니며, 미래 주가나 개인투자자 매수·매도를 예측하지 않습니다. 투자 종목·매매 시점을 추천하거나 댓글과 매매 행동의 인과관계를 판단하는 서비스도 아닙니다.

핵심 데이터
종목·일자별 온라인 댓글, 개인투자자 일별 매수량·매도량 및 매수·매도 우세도
02

실제 서비스 화면

분석 결과가 사용자 화면으로 이어진 모습

실제 배포 서버의 시장 개요, 종목 분석, 연구 소개와 댓글 분석실을 같은 화면 규격으로 기록했습니다.

03

내가 맡은 역할

댓글 처리부터 모델 결과의 서비스 연결까지 담당했습니다

4인 팀의 팀장으로 전체 기술 흐름을 관리했습니다. 동시에 댓글 전처리와 TF-IDF부터 모델 비교·학습·추론, 결과 변환, 일별 댓글·매매 해설, backend와 자동화 통합까지 핵심 분석 흐름을 직접 구현했습니다.

팀장 · 기술 흐름 관리

전체 기술 흐름과 기능 간 통합을 관리했습니다

데이터·모델·서비스 사이의 연결을 기준으로 처리 규칙과 완료 조건을 정리하고, 각 기능이 하나의 서비스 흐름으로 이어지도록 조정했습니다.

  • 기술 흐름 관리

  1. 01

    모델 개발

    후보 비교부터 서비스 모델 관리까지 담당했습니다

    3. 최종 Ridge 선정

  3. 03

    추론 결과를 안전하게 저장하고 재사용하게 했습니다

    3. DB 적재

    학습된 두 댓글 분석 모델의 결과 품질을 확인하고, 재실행해도 기존 결과를 덮어쓰지 않는 추론·저장 계약을 구현했습니다.

  4. 04

    서비스 결과

  5. 05

    Backend & Operation

    분석 기능을 backend와 최상위 실행 흐름으로 통합했습니다

05단계의 동일 TF-IDF Sparse Vector [0, 0.18, 0, 0.42, 0, …] Ridge Regression 이 파이프라인은 모델 입력에서 끝납니다.

왜 종목·일자 단위인가?

모델의 학습 정답이 같은 종목·일자의 개인투자자 매수·매도 우세도이므로, 댓글도 같은 기준으로 묶어 비교 가능한 하나의 입력 단위를 만들었습니다.

학습 전용

06 · B

기술 상세 · 모델 출력에서 서비스 신호까지

LLM을 더 강하게 제어하는 대신 입력과 역할을 다시 설계했습니다

모델 feature를 원댓글 문맥까지 추적하는 시도에서 출발해, LLM 이전 단계에서 해석 가능한 정형 결과를 만드는 구조로 전환했습니다.

  1. 01

    현재 입력의 Feature Contribution 계산

    Ridge coefficient만 보지 않고 TF-IDF × learned coefficient로 실제 입력에서 영향이 큰 feature를 계산했습니다.

  2. 02

    Feature를 원댓글 문맥으로 연결

    형태소 token만으로는 의미를 이해하기 어려워, 주요 feature를 포함한 원댓글 후보를 다시 추적했습니다.

  3. 03

    여러 기여 표현을 포함한 대표 댓글 선정

    상위 feature의 abs(contribution) 합을 selection score로 사용해 대표 문맥을 고르고, 부정·질문 여부도 함께 기록했습니다.

    comment_idtextmatched_featuresselection_scorehas_negationhas_question
  4. 04

    원댓글 문맥을 LLM Evidence로 전달

    LLM이 대표 댓글 전체를 읽고 설명하도록 시도했지만 질문·반어·부정·미래 전망과 투자 조언을 막는 규칙이 계속 늘었습니다.

  5. 05

    문제 재정의

    LLM에게 더 잘 판단시키는 문제가 아니라, LLM 이전 단계에서 사용자가 이해할 수 있는 정형 결과를 먼저 만드는 문제로 바꿨습니다.

  6. 06

    같은 모델의 과거 출력분포와 비교

    현재 raw output을 학습 데이터의 predicted score 분포와 비교해 0~100 상대 신호로 변환하고, 방향과 비교값을 코드에서 확정했습니다.

  7. 07

    LLM은 정형 결과를 문장화

    이미 계산된 방향·댓글·매매 연관 점수·등급·비교값만 전달하고, LLM은 사용자용 일별 설명을 정리하는 역할만 맡겼습니다.

서비스 결과 해석 기준0~100 댓글·매매 연관 점수의 의미

동일 Ridge 모델의 과거 출력분포에서 현재 값이 위치한 상대적 결과입니다.

  • 확률 아님
  • 정확도 아님
  • 미래 개인투자자 매수·매도 예측 아님

기술 상세 · 문제 해결과 설계 판단

서비스로 연결하면서 생긴 세 가지 문제를 이렇게 해결했습니다

각 기능이 따로 동작하는 것과 하나의 서비스로 안전하게 연결되는 것은 달랐습니다. 모델 재현성, 결과의 의미, LLM의 역할에서 문제가 될 지점을 정하고 서비스 기준을 만들었습니다.

01

모델 재현

모델과 입력 기준이 섞이지 않도록 하나의 버전으로 관리

모델 파일 하나가 아니라, 같은 결과를 재현하는 데 필요한 입력 기준까지 하나의 버전으로 관리했습니다.

문제

모델 파일만 저장해서는 같은 결과를 다시 만들 수 없었습니다

다른 학습에서 만든 TF-IDF Vectorizer와 Ridge 모델이 섞이면 같은 댓글도 학습 당시와 다르게 계산될 수 있었습니다.

판단

추론에 필요한 것은 Ridge 파일 하나가 아니라, 학습 당시의 입력 변환 기준과 모델 전체라고 판단했습니다.

해결

한 번의 학습에서 나온 구성요소를 하나의 모델 묶음으로 관리했습니다

TF-IDF Vectorizer, Ridge 모델과 모델·토크나이저·Dataset 버전 정보를 함께 저장했습니다. 추론 전에는 DB에서 선택한 정보와 실제 모델 묶음의 구성이 같은지 확인합니다.

결과

  • 서로 다른 Vectorizer와 Ridge가 섞이지 않도록 검증
  • 어떤 모델 버전으로 분석했는지 결과에서 추적
  • 기존 결과를 덮어쓰지 않고 모델 버전별로 관리
02

결과 의미 구분

같은 모델이라도 댓글 한 줄과 하루치 댓글은 같은 결과로 보여주지 않음

같은 모델을 재사용하더라도 입력 맥락이 다르면 결과 의미도 분리했습니다.

문제

같은 모델을 써도 댓글 한 줄과 하루치 분석의 의미는 달랐습니다

댓글 한 줄에는 같은 종목·일자의 전체 댓글 맥락이 없습니다. 이를 일별 분석과 같은 결과로 보여주면 실제 서비스 결과로 오해할 수 있었습니다.

판단

모델을 호출할 수 있다는 것과 그 값을 같은 의미로 사용자에게 제공할 수 있다는 것은 별개의 문제라고 판단했습니다.

해결

학습 객체는 재사용하되 두 기능의 결과 의미를 분리했습니다

댓글 한 줄 모델 체험은 입력 문장에서 모델이 인식한 표현과 반응만 보여줍니다. 종목·일자별 댓글·매매 연관 결과는 하루치 댓글 분석 경로에서만 제공합니다.

결과

  • 같은 모델을 재사용하면서 입력 맥락별 결과 의미 구분
  • 댓글 한 줄 체험을 일별 댓글·매매 연관 결과로 오해하는 문제 방지
  • 체험 기능과 실제 종목·일자 분석의 역할 분리
03

LLM 역할 제한

LLM이 서비스 분석을 새로 만들지 못하도록 역할 제한

LLM에게 판단을 맡기지 않고, 코드가 계산한 결과를 사용자 문장으로 정리하는 역할만 맡겼습니다.

문제

LLM에게 자유롭게 설명하게 하면 계산하지 않은 내용이 추가될 수 있었습니다

모델 결과를 LLM이 다시 판단하면 입력과 다른 숫자·방향, 미래 전망, 투자 권유나 인과관계 표현이 생성될 위험이 있었습니다.

판단

서비스의 기준은 LLM이 만든 문장이 아니라 코드와 모델이 먼저 계산한 결과여야 한다고 판단했습니다.

해결

코드가 계산한 결과만 전달하고 생성 문장을 다시 검증했습니다

방향·댓글·매매 연관 점수·등급·비교값만 LLM에 전달합니다. 숫자·방향·전망·권유·인과 표현을 검증하고, 근거가 부족하면 LLM 대신 규칙 기반 설명을 제공합니다.

결과

  • 코드가 계산한 결과를 서비스 판단 기준으로 유지
  • 근거와 다른 생성 결과를 저장 전에 차단
  • LLM을 사용할 수 없는 경우에도 규칙 기반 설명 제공
07

자동화와 신뢰성

단계를 연결하는 것보다 실패했을 때 멈출 경계를 먼저 정했습니다

서비스 파이프라인

  1. 01댓글 수집
  2. 02댓글 전처리
  3. 03토큰화
  4. 04종목·일자별 댓글 분석 단위
  5. 05개인투자자 매수·매도 데이터 수집
  6. 06모델 추론
  7. 07일별 LLM 해설 생성

최상위 service pipeline runner가 각 단계의 run_* 함수를 Python 실행 흐름에서 직접 호출합니다. CLI·subprocess를 이어 붙인 체인이 아닙니다.

실패 경계

선행 결과가 유효할 때만 다음 단계로 이동

  • 단계 실패이후 downstream 실행 중단
  • 결과 불완전후속 저장·분석 진행 금지
  • 이전 실행 중non-blocking file lock으로 중복 실행 방지
  • 실행 기록시작·종료와 단계별 반환 상태 기록
08

결과와 한계

구현 결과와 해석 범위를 함께 남겼습니다

구현 결과

문제 해결 뒤 서비스 기준으로 남긴 설계

  • Producer가 확정한 분석 결과를 서비스의 source of truth로 사용
  • DB의 active model과 로컬 artifact identity를 추론 전에 검증
  • 최상위 자동화에서 단계별 실패 경계를 두고 downstream 실행을 중단
  • 분석 계산·DB 저장·서비스 제공 책임을 분리

한계

검증 결과를 서비스 의미보다 크게 해석하지 않았습니다

  • 시간 순서를 강제한 Walk-forward에서는 설명력이 크게 낮아졌습니다.
  • 0~100 댓글·매매 연관 점수는 확률이나 정확도가 아닌 같은 모델 출력분포 안의 상대 결과입니다.
  • 미래 개인투자자 매수·매도 예측이나 댓글과 매매 행동의 인과관계를 의미하지 않습니다.
